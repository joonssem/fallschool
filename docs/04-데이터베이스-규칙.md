# 04. Firebase 데이터베이스 규칙

- 작성일: 2026-09-28
- 대상: Firebase 프로젝트 `eraser-6bb35` Realtime Database (교실 대소동 + 이 게임 공용)
- 규칙 파일: [`firebase/database.rules.json`](../firebase/database.rules.json)

## 1. 왜 고치나

테스트 모드 규칙(`.read: true, .write: true`)은 두 가지 문제가 있다.

1. **누구나 데이터베이스 전체를 읽고 쓰고 지울 수 있다.** 게임 페이지 소스에 설정값이 들어 있으므로, 주소를 아는 사람은 두 게임의 모든 데이터를 지울 수 있다.
2. **만료 날짜가 있으면 그날 두 게임이 동시에 멈춘다.**

## 2. 새 규칙이 하는 일

| 경로 | 누가 | 허용 | 막는 것 |
|---|---|---|---|
| 루트 전체 | — | 없음 | 정해진 경로 밖의 읽기·쓰기 전부 |
| `rooms/{4자리}` (교실 대소동) | 누구나 | 지금과 같은 읽기·쓰기 | 방 번호가 4자리 숫자가 아닌 것, `meta·players·pos·presence·kicks·stats` 외의 항목 |
| `presence/{uid}` (교실 대소동) | 누구나 | 쓰기만 | 읽기, `online` 없는 값 |
| `fallschool/index` | 누구나 | 방 번호·만든 시각 읽기, 새로 쓰기 | 6시간이 안 된 항목 삭제·덮어쓰기 |
| `fallschool/rooms/{4자리}` | 누구나 | 방 하나 단위 읽기 | **방 목록 전체 읽기**, 6시간이 안 된 방 삭제 |
| └ `meta` | 교사 | 방 만들기, 진행 상태 변경 | `hostUid` 바꾸기(방 가로채기), 삭제, 모르는 항목, 잘못된 형식 |
| └ `players/{uid}` | 학생 | 이름(1~8자)·색(#RRGGBB)·진행 숫자 | 긴 글, 모르는 항목 |
| └ `pos/{uid}` | 학생 | 64자 이하 문자열 | 큰 데이터 |
| └ `presence`, `tiles` | 학생 | 숫자(시각) | 다른 형식 |

추가로 이 게임은 교사가 방을 만들 때 **6시간 지난 방을 자동으로 지운다.** 학생 이름이 데이터베이스에 오래 남지 않는다.

## 3. 남는 한계 (정직하게)

두 게임 모두 **로그인(인증)을 쓰지 않아서** 데이터베이스가 "누가" 쓰는지 알 수 없다. 그래서 다음은 규칙으로 막을 수 없다.

- 개발자 도구를 다룰 줄 아는 사람이 **다른 학생의 기록이나 방 상태를 바꾸는 것**
- 교실 대소동 방의 내용 읽기·지우기 (교실 대소동은 오래된 방을 스스로 지우는 기능 때문에 방 삭제가 열려 있어야 함)

이것까지 막으려면 두 게임에 **Firebase 익명 로그인**을 넣고 "자기 uid 경로만 쓰기, 교사 uid만 meta 쓰기" 규칙으로 바꿔야 한다. 교실 대소동 코드 수정이 필요하므로 다음 단계로 둔다.

## 3-1. 변경 기록

| 날짜 | 바뀐 곳 | 내용 |
|---|---|---|
| 2026-09-29 | `fallschool/rooms/{방}/players/{uid}` | `stars`(도전 별 수, 0~10), `gates`(예측 문 첫 시도 결과, `o`·`x`·`-` 최대 8글자) 추가. 교사 화면에 "예측 문 첫 시도 정답 12/21"과 학생별 ★ 표시용. **교실 대소동 경로(`rooms`, `presence`)는 그대로** |

- 게임 코드는 이 두 칸을 다른 진행 기록과 **따로** 보낸다. 새 규칙을 게시하기 전에는 이 두 칸 쓰기만 거부되고, 체크포인트·완주 기록은 그대로 저장된다. 그래서 코드 배포와 규칙 게시 순서가 바뀌어도 게임이 멈추지 않는다.

## 4. 적용 방법 (Firebase 콘솔)

1. [Firebase 콘솔](https://console.firebase.google.com) → `eraser-6bb35` 프로젝트 → **Realtime Database** → **규칙** 탭
2. **지금 규칙 전체를 복사해 메모장에 백업**해 둔다 (문제가 생기면 그대로 되돌리기 위해).
3. 편집기 내용을 모두 지우고 `firebase/database.rules.json` 내용을 붙여 넣는다.
4. **게시** 버튼을 누른다. 문법 오류가 있으면 게시 전에 빨간 표시가 뜬다.
5. (선택) **규칙 플레이그라운드**에서 확인:
   - 읽기 `/` → 거부되어야 함
   - 읽기 `/rooms/1234/meta` → 허용
   - 쓰기 `/hello` → 거부
   - 읽기 `/fallschool/rooms` → 거부, `/fallschool/rooms/1234` → 허용

## 5. 게시 후 꼭 확인할 것

교실 대소동이 지금 배포된 버전(Netlify)과 로컬 파일이 다를 수 있으므로 **실제로 한 판 해 본다.**

- [ ] 교실 대소동: 방 만들기 → 학생 참가 → 라운드 진행 → 결과까지 정상
- [ ] 교실 대소동: 강퇴·재입장 정상
- [ ] 이 게임: 방 만들기 → 학생 참가 → 출발·얼음·경기 끝·대기실로 정상
- [ ] 문제가 있으면 2번에서 백업한 규칙을 다시 붙여 넣고 게시 → 원래대로 돌아간다

## 6. 교실 대소동 호환성 검토 (Codex, 2026-09-28)

교실 대소동 저장소에서 Codex가 모든 HTML(현재 개발판, 배포판, 보관본, 중간 라이브본, ZIP 내부)의 데이터베이스 접근을 정적 분석했다. 에뮬레이터는 쓰지 못했고(Java·Firebase CLI 없음), 실제 Firebase와 데이터는 건드리지 않았다.

**결론: 기능 호환성 조건부 통과, 보안 격리는 별도 개선 필요.** 규칙 파일은 수정하지 않는다.

| 확인 항목 | 결과 |
|---|---|
| 방 만들기, 참가, 위치 동기화, 라운드·결과·통계, 강퇴·재입장, `onDisconnect` 정리, 오래된 방 삭제 | 허용 |
| `rooms/{code}` 아래 항목 | `meta, players, pos, presence, kicks, stats` 6개만 사용 (규칙과 일치) |
| 방 코드 | 항상 1000~9999로 생성, 학생 입력도 4자리 검증 |
| 루트 `presence/{uid}` | 모든 쓰기에 `online` 포함, 다중 경로 update도 병합 결과 기준으로 통과 |

거부되는 것과 조치:

| 거부 | 영향 | 조치 |
|---|---|---|
| 연결 진단용 루트 REST 읽기 `/.json?shallow=true` | 실시간 연결 **실패 시에만** 안내 문구가 부정확해짐 | 교실 대소동 코드에서 `/rooms.json?shallow=true`로 변경 (규칙은 열지 않음) |
| 중간 라이브본의 `/presence` 전체 읽기 | 현재판·배포판에는 없는 기능 | 조치 없음 |
| (잠재) 조작된 localStorage 방 코드·uid | 정상 사용에서는 발생 안 함 | 교실 대소동 코드에서 재사용 전 형식 검사 |

보안 참고: 인증이 없으므로 누구나 교실 대소동 방을 읽기·덮어쓰기·삭제할 수 있다. Firebase 규칙은 상위에서 허용한 접근을 하위에서 취소할 수 없으므로, 이를 막으려면 두 게임에 익명 로그인을 도입하고 uid 기반 규칙으로 바꿔야 한다 (3절의 다음 단계).

알려진 작은 영향: 교실 대소동은 실시간 연결이 **실패했을 때만** 원인 진단용으로 루트(`/.json`)를 읽는데, 새 규칙에서는 거부된다. 연결 실패 시 안내 문구가 "도메인 접속이 완전히 차단" 쪽으로 나올 수 있다. 정상 연결에는 영향이 없다.
