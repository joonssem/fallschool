# 33. 작업 계획 (2026-10-02 기준, Claude 담당)

- 작성일: 2026-10-02. 역할: Codex는 새 맵 제작, Claude는 기존·신규 맵의 교육 내용 확인과 게임성 추가([29](29-Codex-전달-2026-10-02.md) 참고).
- 이 문서는 **계획**이다. 아래 항목은 구현·검토 완료가 아니다. 완료하면 해당 단계 아래에 결과 문서 번호와 날짜를 적는다.
- 공통 원칙: [19](19-게임성-반영-기준.md) 점검표 적용, 자동 시험은 규칙·이동 검증일 뿐 재미·학습 효과의 증거로 쓰지 않는다. 교사 보고·코드 기반 추정·실제 교실 검증을 구분해 기록한다. 선택이라고 안내한 활동은 건너뛸 수 있게, 탈락 없음·안전한 재시도 유지. 커밋·푸시는 사용자가 요청할 때만 한다. Codex의 미커밋 파일(`icetaxi.js`, `echodetective.js`, 각 문서 등)은 건드리거나 커밋하지 않는다. 공통 파일(`kit.js`, `physics.js`, `player.js` 등)을 바꾸면 변경 범위와 호환 영향을 기록한다.

- Codex가 오늘 새 맵 3개를 만들었다: **명령 택배 로봇 도시**(제작 문서 `23-명령택배로봇도시-제작.md`, 커밋됨), **열을 지키는 얼음 택배**(`24-열을지키는얼음택배-제작.md`, 미커밋), **메아리 탐정단**(`30-메아리-탐정단-제작-기록.md`, `echodetective.js`, 미커밋). 이 맵들은 아직 Claude가 검토하지 않았다.
- 문서 번호가 겹친다: 23(2), 24(2), 29(2), 30(2). 정리는 Codex 쪽 파일 정리 뒤에 정한다.

## 단계별 계획 (순서대로)

### 1단계. Codex 새 맵 3개 검토 (최우선)

요청 내용(사용자 전달): 각 맵의 제작 문서와 게임성 기준을 확인하고 교육 내용의 정확성과 게임 플레이를 검토한다. 특히 메아리 탐정단은 음파 반사와 왕복 시간 설명이 적절한지, 게임용 단순 모형이 실제 현상과 혼동되지 않는지 확인한다. 선택이 실제 이동과 결과로 이어지는지, 선택 활동을 건너뛸 수 있는지, 안전한 재시도가 가능한지도 본다. 자동 시험 통과는 재미나 학습 효과의 근거로 간주하지 않고 수정 제안과 교실 관찰 항목을 문서에 정리한다.

작업 순서와 산출물:
1. 읽을 것: 각 제작 문서, `docs/18`·`19`, 맵 코드(`robotcity.js`, `icetaxi.js`, `echodetective.js`), 시험 파일. 안내문·문제·정답 해설·표시 문구를 코드에서 뽑아 읽는다(`docs/22` 방식).
2. 교육 내용 점검 항목:
   - 메아리 탐정단: 소리가 물체에 부딪혀 되돌아오는 반사, 왕복 시간과 거리의 관계(거리 = 속도 × 왕복 시간 ÷ 2의 방향성, 수식 노출 여부), 게임용 시간·거리 단위가 실제 값처럼 읽히는지, 메아리가 안 들리는 경우(너무 가까움·흡수·방향), 안내판의 "모형" 표시, 동굴 벽 재질별 반사 표현의 과장. 박쥐·돌고래 등 생물 예가 있다면 정확성도 확인한다.
   - 열을 지키는 얼음 택배: 열은 높은 쪽에서 낮은 쪽으로 이동, 단열 재료 비교의 공정한 비교 조건(같은 양·같은 시간), 얼음이 녹는 속도가 재료·햇빛·경로에 따라 달라진다는 표현의 방향, "차가움이 이동한다" 같은 오개념 문구, 게임 시간·수치는 모형이라는 표시.
   - 명령 택배 로봇 도시: 명령 순서·반복·회전이 실제 로봇 움직임으로 이어지는지, 용어(명령, 반복, 순서)의 정확성, 정답이 하나뿐인 문제로 오해시키는지.
3. 게임 플레이 점검 항목([19](19-게임성-반영-기준.md) 점검표): 핵심 재미, 의미 있는 선택과 즉시 결과, 선택이 이동·결과로 이어지는지, 선택 활동을 실제로 건너뛸 수 있는지, 재시도 부담(왕복·대기·낙하), 터치 오입력, 기본 완주와 선택 도전, 친구와의 연결, 재체험 용도, 대기 시간. 실제로 코드·시험으로 확인한 것과 추정을 구분한다.
4. 산출물: `docs/34-새맵3개-검토.md`(맵별 판정, 수정 제안 우선순위, 교실 관찰 항목, 미확인 목록). `docs/12`의 7절 뒤에 새 맵 3개의 관찰 항목을 추가한다.
5. 수정 범위: 과학 표현·안내문 오류처럼 작은 수정은 Claude가 직접 하되 Codex 미커밋 파일과 충돌하지 않게 Codex가 커밋한 뒤에 한다(커밋 전이면 제안만 문서화하고 Codex에게 전달). 구조 변경이 필요한 제안은 Codex에게 전달한다.
6. 완료 기준: 3개 맵 모두 점검표와 교육 점검 결과가 문서에 있고, 수정 제안마다 근거(코드 줄·문구)가 있다. 시험 결과는 규칙·이동 검증으로만 적는다.

### 2단계. 태양계 목성·화성 중력 활용 선택 활동 ([32](32-시소안전길-달높이뛰기.md) 후속)

- 목성(게임 ×1.6, 점프 낮음)과 화성(×0.45, 점프 높음, 모래 폭풍)에서 중력 차이를 몸으로 이용하는 선택 활동 1~2개. 달 높이뛰기 탑과 겹치지 않는 선택 결과(예: 화성은 높은 곳 지름길, 목성은 낮은 점프로만 가능한 정밀 경로)를 정한다.
- 조건: 기본 길 유지, 가까운 체크포인트 추가, 기존 시험(`solar-gates.mjs`) 유지, 같은 높이를 다른 중력으로 오를 수 있는지 시험으로 확인, 과학 범위는 기존 해설과 같게(수치 계산 없음).
- 산출물: 구현, 시험, 문서 `docs/36-태양계-중력활용.md`, `docs/12` 관찰 항목.

### 3단계. 점프 연구소 시험 코스 교사용 난이도 조절

- 먼저 **범위 확인**: 방 설정(`meta`) 구조와 `database.rules.json`을 읽고 새 필드가 필요한지 판단한다. 필요하면 호환 영향(기존 방, 규칙 시험)을 기록하고 사용자에게 확인을 받는다.
- 후보 방식: 교사가 시험 구간의 장애물 속도·바람·폭을 단계(쉬움/기본/어려움)로 고른다. 코스 시드처럼 방의 모든 학생에게 같은 값이 전달되어야 한다. 단계별 값은 코드 상수 한 곳에 둔다.
- 완료 기준: 단계에 따라 시험 구간 통과 가능성(`tests/lab.mjs`)이 유지되고, 설정이 없는 기존 방은 기본 단계로 동작한다.

### 4단계. 교실 관찰 정리와 결과 반영 틀

- `docs/12` 7절에 흩어진 관찰 항목(오늘 추가한 활동 약 12개 + 새 맵 3개)을 **한 장 요약표**로 정리한다: 우선 관찰할 5~6개 장면, 기록할 것, 해석할 때 주의.
- 관찰 결과를 받으면 활동별로 유지·수정·삭제를 판단하는 기준을 문서에 둔다(예: 대부분 건너뛰면 보상 보강, 반복 낙하가 많으면 값 조정, "해도 그만"이면 선택 결과와 다음 행동 연결 강화). 결과는 교사 보고와 학생 반응을 구분해 기록한다.
- `docs/14` 7번(도움 요청 표시)은 관찰에서 "누가 막혔는지 못 찾는다"가 나올 때만 검토한다.

### 5단계. Codex 조율과 정리

- 문서 번호 겹침 정리: Codex가 자기 문서를 옮기거나 새 번호(35 이후)를 쓰도록 요청한다. 링크는 파일명 기준이라 깨지지 않지만 번호가 모호하다.
- `package.json`·`index.js`·`docs/19` 같은 공유 파일은 둘 다 수정하는 파일이라 한 쪽씩 커밋하고 겹치면 두 쪽 항목을 모두 남긴다(지금까지 방식).
- `kit.js` 공용 장치 추출(`docs/14` 4번)은 교실 관찰 전에는 하지 않는다. Codex가 `kit.js` 변경 계획이 있으면 범위를 먼저 알려 달라고 요청해 두었다.
- 사용자 요청 시에만 커밋·푸시. 푸시 전에 `git fetch`로 원격 변경을 확인한다.
