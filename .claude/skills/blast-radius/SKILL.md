# 영향 범위 점검 (blast-radius)

공통 파일을 바꾸면 그 파일을 쓰는 **모든 맵**이 같이 바뀐다. `grep`으로 호출한 곳을 나열하는 것은 일이 아니다. 목록은 1초면 나온다. 할 일은 **grep이 못 보여 주는 깨짐**을 찾는 것이다.

> 출처: Cursor `pstack`의 `blast-radius`(MIT)를 이 프로젝트에 맞게 고쳤다. 지침 근거는 `AGENTS.md`의 "공통 파일 변경이 필요하면 변경 범위와 호환 영향을 기록한다", "공용화는 각 맵의 고유한 플레이를 보존한다".

## 먼저 알아 둘 것: 공유 모듈 지도

`prototype/src` 기준(2026-10-19 확인, 맵이 늘면 바뀐다. 다시 센다).

| 파일 | 불러오는 곳 | 바꾸면 흔들리는 것 |
|---|---|---|
| `levels/kit.js` | 맵 파일 약 20개 | 발판·문·체크포인트·별 등 거의 모든 맵 |
| `levels/variants.js` | 맵 파일 약 13개 | 시드·섞기. **바꾸면 같은 시드의 배치가 달라진다** |
| `physics.js` | `level.js` 등 + 시험 7개 | 충돌·낙하·턱(0.15m) 판정 → 걸어서 오르는 길 |
| `player.js`, `level.js`, `wind.js` | 본체 + 시험 | 이동·부활·바람 |
| `levels/index.js` | 맵 등록 | 등록하면 `tests/map-rules.mjs`가 자동 검사 |
| `net/*` | 방 동기화(Firebase/로컬) | 교사 화면·학생 기록·`firebase/database.rules.json` 상한 |

시험으로 막히지 않는 곳(주의): `input.js`, `remote.js`, `sfx.js`는 시험이 없다. 화면·iPad 입력은 자동 시험이 못 본다.

## 원칙: 쓴 글을 믿지 말고 하나를 증명한다

그럴듯한 영향 분석 글은 맞든 틀리든 설득력 있게 읽힌다. 그래서 글을 건네지 말고, **"이 변경이 안전한 이유가 되는 사실 한두 개"**를 찾아 코드를 실행해 증명한다.

각 사실을 아래 단계 중 싸게 갈 수 있는 데까지 올리고, **어디서 멈췄는지** 적는다.

1. 말만 했다 — 가치 없음.
2. 실제 `파일:줄`을 가리켰다.
3. 나쁜 경우가 일어날 수 없음을 단계별로 따라가 보였다.
4. **실행했다** — 실제 코드를 불러 틀리면 크게 실패하는 짧은 스크립트·시험(보통 `prototype/tests` 방식).
5. 실제 화면에서 재현했다(브라우저·iPad). 자동 시험으로는 여기까지 못 간다.

### 4단계에 오르기 전에: 이 검사가 틀린 변경을 볼 수 있는가

"변경 전/후 차이 없음"은 **검사가 그 차이를 볼 수 있을 때만** 안전의 증거다. 비교 도구를 믿기 전에 두 가지를 확인한다.

- **기준선이 재현되는가**: 변경 전 코드를 두 번 돌려 결과가 같은지 본다. 맵이 만드는 3D 객체의 `uuid`처럼 실행마다 바뀌는 값이 지문에 섞이면 변경 전끼리도 달라진다(2026-10-19 시험에서 체크포인트의 `flag` 객체가 그랬다).
- **검사가 변경을 보는가**: 일부러 틀린 변경을 넣어 검사가 **실패하는지** 본다. 충돌체·체크포인트 지문은 유물·정답 배치 같은 상태값을 못 봤고, `npm test`도 통과했다. 보는 것이 변경과 같은 곳에 있는지 확인한다.

## 절차

1. **변경을 읽는다.** diff, 추가·변경·삭제한 심볼, diff에 안 쓰인 동작 변화(기본값, 순서, 반환 형태).
2. **안전의 근거 하나를 찾는다.** 위험해 보이는 변경도 대개 한 사실 때문에 안전하다("이 인자는 기존 맵이 안 넘긴다", "새 분기는 옵션을 켠 맵에서만 탄다"). 그것이 성립하면 대부분이 한꺼번에 정리된다. 막연한 위험 목록보다 여기에 시간을 쓴다.
3. **grep이 멈추는 곳을 본다.**
   - **시드·무작위**: `variants.js`/`rngFor`의 호출 순서가 바뀌면 같은 시드의 배치·정답이 바뀐다. 시드로 외워서 풀 수 없게 한 설계(`AGENTS.md` 설계 확인)가 깨지거나, 반대로 기존 맵의 정답 위치가 이동한다. `rngFor`·`shuffled`·`pick`의 결과는 `tests/variants-seed.mjs`가 고정해 두었다. 이 시험이 실패하면 **의도한 변경인지** 먼저 판단하고, 의도한 변경이면 기대값과 문서를 함께 고친다. 그냥 기대값만 고쳐 통과시키지 않는다.
   - **새 코드와 옛 코드가 한 방에 섞임**: 시드는 교사가 `meta.seed`에 저장해 방 전체가 공유한다(`net/room.js`). 시드로 만든 문제 구성이 바뀌는 변경은, 캐시된 화면(iPad 등)과 새 화면이 같은 방에 있으면 학생마다 다른 문제를 보게 한다. 배포 후 화면 새로고침 안내가 필요한지 적는다. 이 위험은 코드를 읽은 추론이며 실제 기기에서 재현한 것이 아니다.
   - **물리·이동**: 충돌 상자 크기, 턱 높이(0.15m 안팎), 발판 반응 거리(`onStand`는 서 있는 동안 매 프레임). 모양 단서를 `scale`로 바꾸면 충돌 상자도 바뀐다.
   - **고유한 플레이 보존**: 공용화가 맵별 고유 판단(조작 → 결과 → 다음 이동)을 하나의 틀로 뭉개지 않는가.
   - **저장·교사 화면**: 별 개수 상한 10(`firebase/database.rules.json`), 교사 화면이 읽는 필드 이름·형태, 로컬/Firebase 백엔드 두 곳이 같은지.
   - **교실 규칙**: 탈락 없음, 밀치기·잡기 없음, 안전한 재시도, 선택 활동은 실제로 건너뛸 수 있음.
   - **문서·색인**: `docs/55` 맵·문서 색인, `maps-meta` 시험이 보는 맵 id·설명(24자 이하)·분류.
   - 변경 파일과 다른 에이전트(Codex)의 작업 중 파일이 섞이지 않았는지.
4. **위험마다 정직하게 적는다.** 일어날 가능성과 일어났을 때의 비용, 실제 `파일:줄`. 검색 결과가 없다는 것도 답이다. 없는 호출자나 API를 지어내지 않는다. 확인한 위험과 확인 후 정리한 위험을 나눠 적는다.
5. **핵심 사실을 증명한다.** 짧은 스크립트·시험을 실제로 돌리고 결과를 붙인다. 가능하면 변경 전/후를 같은 시드로 비교한다(예: 여러 맵을 같은 시드로 `build` 한 뒤 배치 값이 같은지).
6. **`npm test`를 `prototype`에서 돌린다.** 전체가 통과해도 그것은 **규칙·이동 검증**이다. 재미·학습 효과·교실 반응의 증거로 쓰지 않는다.

## 돌려줄 형식

- **무엇이 바뀌나** — diff에 드러나지 않는 부분 포함.
- **안전한 이유가 되는 사실 하나** — 단계(1~5 중 어디까지)와 증명. 증명 못 했으면 `미증명`이라고 쓴다.
- **위험** — 깨지는 방식, `파일:줄`, 가능성·비용, 확인 방법.
- **확인 후 정리됨** — 무엇을 확인했고 왜 괜찮은가.
- **합치기 전에** — 진짜 버그를 가장 싸게 잡는 시험·재현(쓴 스크립트 포함).
- **근거 구분** — 코드·봇 시험 / 교사 보고 / 화면·iPad·교실 미확인을 나눠 쓴다(`AGENTS.md`).

공통 파일을 실제로 바꾼 경우, 위 내용을 해당 작업 기록 문서(docs)의 "변경 범위와 호환 영향"에 옮긴다.
